# JJ BLINKS — online store

International e-commerce for JJ BLINKS (autogele, turbans, fascinators, Zara caps, traditional men's caps, stoning and embellishment, branded T-shirts and polos, bridal and occasion headwear, custom and bulk orders).

- **Stack:** Next.js 16 (App Router, React Server Components), JavaScript/JSX only, Tailwind CSS v4, Neon Postgres through the official `@neondatabase/serverless` driver with hand-written SQL (no ORM), Vercel Blob, Paystack, Bun.
- **Runtime dependencies (6):** `next`, `react`, `react-dom`, `@neondatabase/serverless`, `@vercel/blob`, `nodemailer`. **Dev:** `tailwindcss`, `@tailwindcss/postcss`.
  - Password hashing uses Node's built-in `crypto.scrypt`, so there is no hashing package. Validation is hand-written (`lib/validation.js`), so there is no schema library.
  - `nodemailer` is included because Node has no built-in SMTP client.

## 2. What the store does

**Storefront**
- An editorial homepage. Every section is editable in the admin.
- Shop with search, collection, price and availability filters, sorting and pagination.
- Product pages with a gallery, variant selection, stock-aware add to bag, and customer customisation fields.
- WhatsApp enquiry links, approved reviews only, related products, and Product and Breadcrumb structured data.
- New-in and best-seller pages. Best sellers are ranked only by verified paid orders and stay empty until there are sales.

**International**
- Currency selector (NGN, USD, GBP, EUR, CAD). Non-NGN amounts appear as "≈ indicative" next to the NGN price, using a stored and time-stamped exchange-rate snapshot. Conversions are hidden when no source is set up or the rate is more than 48 hours old.
- Checkout always states the charging currency, and notes that the customer's bank may convert it.
- Country-aware addresses: a searchable country picker; a Nigerian state list; ZIP, postcode or postal code labels and validation; the postal field hidden where countries don't use one; and international phone numbers normalised to `+country` format.
- Configurable shipping zones and methods:
  - pricing can be flat, by weight, by order value, pickup, or manual quotation;
  - free-shipping thresholds, delivery estimates, carrier names and restricted destinations;
  - a rest-of-world zone, which is off by default.
- Customs and duties notice on product pages, at checkout, and on the shipping and terms pages.

**Checkout and payments**
- Guest checkout, coupons, and a server-side re-quote on every change.
- Stock is reserved with an atomic conditional update when the order is placed, and released if payment isn't completed in the configured window.
- Paystack is used through its redirect checkout. Payment is confirmed only after a server-side `transaction/verify` call that matches the reference, amount and currency.
- Webhooks are signature-checked (HMAC-SHA512), de-duplicated and re-verified.
- Duplicate charges are flagged for refund, never double-fulfilled.
- For destinations on manual quotation, the customer orders first and pays from a link once the admin sets the delivery cost.

**Accounts**
- Sign in with **email or phone number** and password, or with **Google** or **Facebook**. Password fields have a show/hide toggle.
- Register, password reset (by email or phone, link sent to the account's email), saved addresses, order history and wishlist.
- Customers can connect or disconnect Google and Facebook, and accounts created through them can set a password later.
- Sessions are HTTP-only cookies; only a SHA-256 hash of the token is stored. Changing or resetting the password signs out every device.

**Custom and bulk orders**
- Request forms with reference-photo and logo uploads, apparel sizes and branding fields.
- Workflow: new → reviewing → quoted → approved → in production → ready → completed (also rejected and cancelled).
- The customer accepts a quotation from their private link, which creates a payable order for exactly the quoted amount. Nothing is charged before that.

**Admin (`/admin`)**
- Dashboard with verified-revenue summaries (gross, discounts, refunds, net), queues and low stock.
- Orders: fulfilment, tracking, shipping quotes, refunds through Paystack or recorded manually, notes, and a "check with Paystack" reconciliation button.
- Products: photos with upload, replace, reorder, alt text and delete; variants; cost price, which only roles allowed to see costs can view.
- Collections, inventory adjustments with reasons, customers, discount codes, review moderation, custom and bulk requests, shipping, homepage and page content, store settings, staff roles, audit log, sales analytics and contact messages.

**Roles** (`lib/permissions.js`) — every admin page and server action checks permissions on the server.

| Role | Can |
|---|---|
| `super_admin` | Everything, including staff management and payment settings. |
| `admin` | Everything except staff management and payment settings. |
| `inventory_manager` | Products, collections, inventory, photos and reviews. No revenue figures or cost prices. |
| `order_manager` | Orders, customers, custom requests and messages. No refunds, no product editing. |
| `customer` | No admin access. |

## 3. Local development

You need Bun ≥ 1.1 and Node ≥ 22. Node 22 or later provides the global `WebSocket` that Neon's transaction pool uses.

```bash
bun install
cp .env.example .env.local        # or: vercel link && vercel env pull .env.local
```

**Database.** The Neon serverless driver talks HTTP and WebSocket to Neon; it cannot connect to a plain local Postgres. For local development, create a **Neon development branch** (free) and put its connection string in `DATABASE_URL`. Then run:

```bash
bun run db:migrate                 # creates the tables (tracked in schema_migrations)
bun run db:seed                    # real business structure: categories, shipping zones (manual-quote)
bun run db:seed-dev                # OPTIONAL sample products/rates/coupon, clearly marked "Sample"
ADMIN_EMAIL=you@example.com ADMIN_NAME="Your Name" bun run admin:create   # prompts for a password
bun dev                            # http://localhost:3000  ·  admin: /admin/login
```

- Without `BLOB_READ_WRITE_TOKEN`, development uploads go to `public/uploads/dev/`, which is git-ignored.
- Without SMTP, nothing is emailed, and the interface says so.
- Remove the sample data before launch with `bun run db:remove-samples`.

## 4. Deploying to Vercel

1. **Import the repository** in Vercel. The framework preset is Next.js; Vercel detects Bun from `bun.lock`.
2. **Database:** in the project, go to **Storage → Create → Neon (Marketplace) → connect to this project**. Vercel then injects the connection variables, including `DATABASE_URL`, into every environment. Optionally, enable Neon preview branches for preview deployments.
3. **Images:** go to **Storage → Create → Blob → connect to this project**. This injects `BLOB_READ_WRITE_TOKEN`.
4. **Environment variables** (Settings → Environment Variables):

   | Variable | Value |
   |---|---|
   | `APP_URL` | `https://your-domain` (no trailing slash) |
   | `PAYSTACK_SECRET_KEY` | `sk_test_…` first, then `sk_live_…` |
   | `CRON_SECRET` | a long random string (`openssl rand -hex 32`) |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | optional — Google sign-in (section 7a) |
| `FACEBOOK_APP_ID`, `FACEBOOK_APP_SECRET` | optional — Facebook sign-in (section 7a) |
   | `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM` | business Gmail + app password (section 7) |

5. **Run migrations against production** from your machine:
   ```bash
   vercel env pull .env.production.local --environment=production
   bun --env-file=.env.production.local scripts/migrate.js
   bun --env-file=.env.production.local scripts/seed.js
   ADMIN_EMAIL=… bun --env-file=.env.production.local scripts/create-admin.js
   ```
6. **Deploy.** `vercel.json` schedules `/api/cron/maintenance` daily at 03:00 UTC. That job:
   - expires unpaid orders and returns their stock;
   - clears old rate-limit rows and sessions;
   - deletes abandoned anonymous uploads.

   Unpaid orders are also expired whenever someone checks out, so the daily schedule is enough on the Hobby plan.
7. Sign in at `/admin/login`, then work through **Settings**, **Shipping**, **Collections**, **Products** and **Homepage & pages**.

## 5. Paystack setup (merchant dashboard)

1. **Settings → API Keys & Webhooks**
   - Copy the **secret key** into `PAYSTACK_SECRET_KEY`. The public key is not needed: the store uses Paystack's hosted redirect checkout.
   - Set the **Webhook URL** to `https://your-domain/api/webhooks/paystack`. Use the matching test or live URL for each mode.
   - Paystack signs webhooks with your secret key, so there is no separate webhook secret.
   - You do not need a dashboard callback URL. The store sends `https://your-domain/checkout/verify` with each transaction.
2. **International cards:** ask Paystack to enable international payments on the account and run a test charge with a foreign card before advertising it. Customers abroad are charged in NGN unless you enable USD below; their bank converts.
3. **USD charging (optional):** only after Paystack confirms USD is enabled for your business, turn on **Admin → Settings → Payments → Offer payment in USD**.
   - This needs an exchange-rate source (live or manual).
   - The USD amount is calculated from that rate, rounded up, and fixed on the order.
   - GBP, EUR and CAD are display-only. The site never implies a charge in those currencies.
4. **Refunds:** "Refund through Paystack" calls Paystack's Refund API. Refunds can also be recorded when they were made elsewhere.
5. **Going live:** switch to live keys and the live webhook URL. Place one real low-value order, refund it, and check the order history in the admin.

## 6. Exchange rates

**Admin → Settings → Currency display** offers three options:
- **None** — show NGN only. This is the default.
- **Live** — daily rates from ExchangeRate-API's open endpoint (`https://open.er-api.com/v6/latest/NGN`; no key needed). Fetched at most every 12 hours and stored in `fx_snapshots`. The footer attribution the provider requires is shown automatically.
- **Manual** — rates you type in, as "₦ per 1 unit", with the time they were changed.

Orders record the indicative snapshot the customer saw and, for USD charges, the rate used.

## 7a. Google and Facebook sign-in

The buttons appear on the sign-in and registration pages only after both keys for a provider are set. The flow is OAuth 2.0 authorisation code, written with `fetch` and `node:crypto` (`lib/oauth.js`), so no auth library is involved. It uses a state cookie against cross-site forgery, PKCE for Google, a server-side code exchange, and `appsecret_proof` for Facebook Graph calls.

**Google** (Google Cloud Console → APIs & Services):
1. Configure the **OAuth consent screen** as External, with the app name, support email and the privacy and terms URLs (`/privacy`, `/terms`). The scopes needed are `openid`, `email` and `profile`.
2. Under **Credentials → Create credentials → OAuth client ID**, choose Web application.
3. Add authorised redirect URIs `https://your-domain/api/auth/google/callback` and, for development, `http://localhost:3000/api/auth/google/callback`.
4. Copy the client ID and secret into `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`.

**Facebook** (developers.facebook.com → My Apps → Create app → Facebook Login):
1. Under **Facebook Login → Settings**, add the valid OAuth redirect URI `https://your-domain/api/auth/facebook/callback`.
2. Request the `email` and `public_profile` permissions.
3. Under **App settings → Basic**, copy the App ID and App Secret into `FACEBOOK_APP_ID` and `FACEBOOK_APP_SECRET`, and add the privacy policy URL.
4. Switch the app to **Live**. Meta may ask for business verification first. The code uses Graph API `v26.0` (`FACEBOOK_GRAPH_VERSION` in `lib/oauth.js`); update it when Meta retires that version.

**Account rules** (`resolveSocialLogin` in `lib/session.js`):
- Accounts are matched on the provider's permanent user ID, not the email.
- A first-time Google sign-in whose **verified** email matches an existing customer account is linked to it.
- Facebook is **never** linked to an existing account automatically. The customer signs in with their password and connects Facebook from **Account → Details & password**. This stops someone else's Facebook account from taking over an account with the same email.
- Staff accounts are never linked automatically. The admin sign-in page stays password-only (email or phone).
- If Facebook shares no email, or Google's email is unverified, the customer is asked to register with email instead.
- A customer cannot disconnect their last way to sign in.

The buttons are text-only ("Continue with Google" / "Continue with Facebook"). If you want the providers' official logos, add them from Google's and Meta's brand resources, following their guidelines.

## 8. Backups and recovery

- **Neon point-in-time restore:**
  - Neon keeps history for your plan's restore window.
  - To recover, create a branch from a timestamp before the incident in the Neon console, check it, then restore or repoint `DATABASE_URL`.
  - Check your plan's retention period in the Neon console.
- **Logical backups:** run these regularly and keep them off-site.
  ```bash
  pg_dump "$DATABASE_URL_UNPOOLED" --format=custom --no-owner -f jjblinks-$(date +%F).dump
  pg_restore --no-owner --dbname "$TARGET_DATABASE_URL" jjblinks-YYYY-MM-DD.dump
  ```
  Use the unpooled connection for `pg_dump`.
- **Images:** files live in Vercel Blob and their URLs live in Postgres. Restoring the database does not restore deleted Blob files, so for a full backup also download the Blob store (for example with `vercel blob list`, then fetch the files).
- **Before risky changes:** create a Neon branch, run migrations there first, and test against a preview deployment.

## 9. Tests

```bash
bun run test:unit                                                     # no database needed
JJB_TEST_DATABASE_URL=postgresql://user:pass@localhost/throwaway bun run test:integration
```

- The integration suite **wipes** the database it is given. Point it at a disposable local PostgreSQL ≥ 14 with `psql` installed.
- It runs the application's real SQL through a test-only `psql` driver (`tests/support/psql-driver.js`).

**Results from this build (PostgreSQL 16.15, Node 22.23): 46 tests, 46 passed, 0 failed.**

The tests prove:
- Cart prices from the browser are ignored; drafts and unknown products are rejected.
- Variant pricing, per-variant stock and required customisation fields are enforced.
- Blocked, unserved, weight-based and manual-quote destinations behave correctly.
- Guest checkout is idempotent: a double submit makes one order and one stock reservation.
- **No overselling:** two concurrent sessions race for the last item and only one wins.
- Coupon usage limits hold.
- Payment confirmation:
  - an underpayment is rejected and flagged;
  - only a verified, matching charge marks the order paid;
  - confirmation is idempotent;
  - a second charge is flagged and the database blocks a second successful payment.
- Webhooks reject bad and tampered signatures, ignore duplicates, and never store card data.
- Unpaid orders expire, returning stock and coupon uses; a late payment re-reserves the stock.
- Shipping-quote, fulfilment, cancellation and refund flows work, including rejecting over-refunds.
- Custom orders:
  - no payment before a quotation;
  - the wrong link token is rejected;
  - acceptance creates an order for exactly the quoted amount;
  - one visitor cannot attach another visitor's uploads.
- Order access works only with the token, the owning account, or the order number plus matching email.
- Catalogue search treats SQL-like input as plain data.
- Database constraints block negative stock, fake discounts, bad statuses and inconsistent line totals; failed transactions roll back.
- Sessions:
  - session and reset tokens are hashed;
  - reset links work once;
  - sessions are revoked after a reset;
  - deactivated accounts cannot sign in.
- Rate limits are shared through the database.
- Sign-in works with an email or a phone number in national or international format, and a phone number can belong to only one account.
- Social sign-in:
  - accounts are keyed on the provider's user ID;
  - only verified Google emails auto-link, Facebook never does, and staff accounts never do;
  - deactivated accounts are refused;
  - an identity can't be attached to two accounts;
  - the last sign-in method can't be removed;
  - a social-only account can set its first password.
- OAuth authorisation URLs, PKCE and profile mapping are correct.

## 10. Security notes

- Secrets are only read on the server. The only browser-visible configuration is public content from the database.
- SQL always uses bind parameters. Dynamic `ORDER BY` uses a fixed allow-list (`db/queries/catalog.js`).
- Server actions use Next.js's built-in origin check. The upload route checks `Origin` and `Host` itself.
- Uploads: file type is detected from magic bytes; only JPG, PNG and WebP are accepted, plus PDF for logos. SVG is refused. Files must be 4 MB or smaller and get random object names.
- Rate limits cover sign-in, registration, password reset, checkout, order lookup, uploads, contact, newsletter, reviews and custom requests.
- Security headers include CSP, HSTS, `X-Frame-Options: DENY`, `nosniff`, a referrer policy and a permissions policy (`next.config.mjs`).
- Every staff action is written to `audit_logs`.
